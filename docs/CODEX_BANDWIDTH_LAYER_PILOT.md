## 0. 目的

检验带宽约束能否让 persona 犯出"调用失败型"错误：某条 persona 自己地图里有的经验/某条栈里有的判断，因带宽筛选未进入该次调用的 context，导致决策偏离——且偏离方向与该 persona 的认知风格一致。这是 overload 机制的第一次代码化验证，不是校准，不是复现真人盈利率。

## 1. 带宽层实现（新模块 `scripts/analysis/bandwidth_layer.js`，确定性、可审计）

对 B 条件的每次 LLM 调用，在拼 prompt 前执行：

### 1.1 地图检索预算（替代全量注入）
- 当前调用的"决策焦点文本" = 该步任务描述 + 栈中最近 1 条记录的摘要
- 用现有 embedding 基础设施（`embeddingService.js` / `vpWordScorer.js` 的相似度机制，不新造）计算 50 条地图条目与焦点文本的相似度
- 近因加权：栈中最近 2 条记录里出现过的主题（用现有 THEME_RULES 判定），相关地图条目相似度 ×1.2
- 取 top-B 条进入 prompt，其余丢弃

### 1.2 负载递减
`B = max(B_min, B0 - λ × stack_len)`，试探值：**B0=20, λ=3, B_min=8**（R1 时栈长 0→B=20；D5 时栈长约 4→B=8）。含义：决策链越深，可同时调用的经验越少。

### 1.3 栈摘要化（验算回路弱化）
B 条件下，D4/D5 收到的栈不再是全文，而是每条记录压缩成一行摘要（用现有 makeStackRecord 的摘要逻辑，若粒度不够则截断到每条 ≤50 字）。R1/Coach/D3 栈较短，保持全文。含义：晚期决策看不清早期决策的细节依据，只记得结论。

### 1.4 审计落盘（硬性要求）
每次调用逐条记录：焦点文本、50 条地图各自的相似度分、入选/落选、落选原因（预算外/低相关）、B 值、栈摘要前后对照。**没有这份审计，实验结果无法解读，缺失即验收不通过。**

### 1.5 不做的旋钮（留下轮）
位置埋没（lost-in-the-middle 利用）本轮不做——它与检索预算叠加会导致归因混乱，单变量优先。

## 2. 参数（全部试探值，记入 meta）

| 参数 | 值 | 含义 |
|---|---|---|
| B0 | 20 | 初始检索预算（全量 50 的 40%）|
| λ | 3 | 每深入一步递减 3 条 |
| B_min | 8 | 预算下限 |
| 近因加权 | ×1.2 | 最近主题的相关条目提权 |
| 栈摘要 | D4/D5 生效，每条 ≤50 字 | 验算回路弱化 |

两个 persona 用同一套参数——本轮先验证机制本身产生效果，persona 差异化参数（草根 B 更小等）留给校准轮。

## 3. 矩阵

2 persona × {B 带宽约束, F 无限带宽} × 1 次 = **4 条完整链**（F 条件若与 full_game v2 的对应链完全同装置同锦囊，可直接复用 v2 已有结果不重跑，Codex 核实装置一致性后决定，记入 meta）。

## 4. 判决指标（N=1/格，全部描述性）

1. **调用失败的直接证据（主判决）**：对照审计日志——B 链中是否存在这样的时刻：某条地图经验/栈细节被预算挡在门外，而 F 链同一决策点该信息在场且决策不同。逐例列出：被挡信息、该步决策差异、方向是否符合该 persona 认知风格
2. **决策轨迹对照**：B vs F 的格子选择/VP/选卡/定价逐项并排（同 persona 内对照）
3. **经济后果**：4 条链 profit/Q 并排；B 链是否更差、差在哪一环
4. **元认知泄漏检查**：B 链理由文本是否出现"我可能遗漏了什么"类表述（出现=机制被察觉，如实记录）
5. 一句话观察：带宽约束是否产生了"知识在库里但没被调用"的真实案例——overload 代码化可行性的第一个数据点

## 5. 验收

1. 4/4 链完成（或 2 条 B 链完成 + 2 条 F 链复用 v2，装置一致性已核实）
2. B 条件全部 prompt 通过 assertInfoSet（带宽层未引入白名单外信息）
3. 1.4 审计日志完整落盘，每次调用的入选/落选清单可查
4. 四件套产物 + meta（参数表、种子、复用的锦囊、全部 sha256）
5. summary 明确标注：参数为试探值未经真人 trace 校准，结果为机制验证非保真度声明
